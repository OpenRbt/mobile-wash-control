Для закрытия этих пунктов в корень проекта положен скрипт **`verify_release.sh`** — он прогоняет всю цепочку команд и складывает логи в `audit_logs/`.

**Попытка прогона 18.09.2026, 08:11 UTC — все 9 шагов упали с `exit 127` [ПРОВЕРЕНО]:**

```
audit_logs/version.log:  ./verify_release.sh: line 18: flutter: command not found
```

Это не ошибка сборки, а **отсутствие Flutter SDK на машине разработчика**. Причина установлена: `android/local.properties` содержит `flutter.sdk=/private/tmp/codex_flutter_sdk/flutter`, то есть SDK, которым собирался APK 4 сентября, лежал в `/private/tmp` — macOS очищает этот каталог при перезагрузке. В домашнем каталоге Flutter нет ни в одном из типовых мест (`~/flutter`, `~/development/flutter`, `fvm`, `puro`, Homebrew-каталоги). Android SDK при этом на месте: `~/Library/Android/sdk`, и `~/.pub-cache` сохранён.

**Это самостоятельная находка аудита, а не помеха ему:** окружение сборки проекта невоспроизводимо. Пути к SDK живут во временном каталоге и в файле, которого нет в git; CI отсутствует; единственный воспроизводимый путь сборки — `Dockerfile.android` с закреплённым образом `instrumentisto/flutter:3.41.6-androidsdk36-r0`. См. пункт 12 раздела 16.

Скрипт доработан: теперь он сам ищет SDK (PATH, типовые каталоги, fvm, puro, Homebrew, `flutter.sdk` из `local.properties`), принимает явный путь через `FLUTTER=...`, а если локального SDK нет — прогоняет всю цепочку **внутри закреплённого Docker-образа проекта**.

## 1. Краткий итог

**MobileWash (`mobile_wash_control`) — это не потребительское приложение автомойки.** Это внутренний операторский/административный клиент для серверов автомоек OpenRbt: он ищет wash-сервер в локальной сети, авторизует оператора по PIN и даёт управлять постами, программами мойки, скидками, кассой, скинами, пользователями и смотреть статистику инкассаций. Услуги не продаются, заказы не создаются, платежи не проводятся — разделы SBP и «Бонусы» показывают только статус сервисов.

Это меняет весь разговор о публикации: значительная часть требований Play (оферта, платёжные данные, удаление аккаунта конечного пользователя) к такому приложению относится иначе, чем к маркетплейсу услуг.

**Состояние по существу:**

* Техническая база в хорошем состоянии: `targetSdk 36` (уже удовлетворяет дедлайну 31.08.2026), три ABI включая 64-бит, R8 включён, иконки и adaptive icon на месте, локализация ru/en полная, устаревших Flutter API после апгрейда не найдено.
* **Публикацию блокируют три вещи**: release-сборка подписана отладочным ключом; в манифесте объявлено `REQUEST_INSTALL_PACKAGES` без допустимого по политике Play сценария; в проекте вообще нет Privacy Policy, без URL которой Play Console не даст отправить релиз.
* Отдельно: в коде найдены реальные дефекты — «мёртвая» кнопка входа при любой ошибке сервера, утечка бесконечного опроса сервера, отсутствие таймаутов у API-клиента. Они не блокируют модерацию, но блокируют нормальную эксплуатацию.

Часть находок уже исправлена в рамках этой сессии — см. раздел 19.

## 4. Публичная оферта

> **Публичная оферта в текущем проекте не обнаружена.**

Поиск по всему репозиторию (`lib/`, `assets/`, `web/`, `android/`, `README.md`) по терминам *оферт*, *соглашен*, *terms*, *offer*, *agreement*, *consent*, *EULA*, *согласи* дал **ноль** совпадений по существу (единственное попадание — слово «offers» в шаблонном тексте README про Flutter).

Отсутствует всё: документ, экран, ссылка в UI, чекбокс согласия, запись факта и версии принятия.

**Нужна ли она этому приложению технически — разбор по фактическому функционалу [ПРОВЕРЕНО]:**

| Признак, при котором оферта обычно нужна | Есть в MobileWash? |
| --- | --- |
| Продажа услуг мойки конечному клиенту | Нет |
| Приём платежей в приложении | Нет |
| Создание заказов клиентом | Нет |
| Платные подписки, списания с карт | Нет |
| Свод клиента и исполнителя | Нет |
| Выставление счетов/чеков клиенту | Нет |
| Отмены и возвраты | Нет |

Приложение работает **после** авторизации оператора по PIN на сервере конкретной мойки. Страницы `sbp_status.dart` и `bonus_status.dart` — **только чтение статуса** сервисов (`available`, `isConnected`, `lastErr`, `unpaidStations`); ни один вызов не инициирует платёж. Раздел «Статистика» показывает отчёты по инкассации — это бизнес-данные владельца мойки, а не платёжные данные потребителя.

**Разделение, как просили:**

* **A. Технические/сторовые требования.** Google Play отдельно *оферту* не требует. Он требует Privacy Policy (см. раздел 5). Если публиковаться публично — в листинге понадобится описание того, что приложение предназначено для сотрудников мойки, иначе модерация может закрыть его как неработающее без оборудования (см. раздел 17, App access instructions).
* **B. Вероятные коммерческие/правовые требования.** Оферта — это договор с конечным потребителем. Здесь конечного потребителя в приложении нет. Скорее нужны условия использования ПО (лицензионное соглашение / EULA) между OpenRbt и владельцем мойки, но это отношения вне приложения.
* **C. ### 6.3 Про требование удаления аккаунта

Требование Play распространяется на приложения, **позволяющие пользователю создать аккаунт внутри приложения**. Здесь ситуация пограничная и зависит от способа публикации:

* аккаунты операторов заводит **администратор мойки** в `lib/mobile/pages/users/editUser.dart`, самостоятельной регистрации нет;
* удаление существует — `Repository.deleteUser()` → `lib/repository/lea_central_wash_repo/repository.dart:1165` → `api.deleteUser(args)`, с диалогом подтверждения на `editUser.dart:98`. Но это админ удаляет оператора, а не пользователь себя. **Трассировка до backend не выполнена — нет доступа к серверу [ПРЕДПОЛОЖЕНИЕ]**;
* официальные исключения из требования: permanently private apps и enterprise device management apps.

**Практический вывод:** если публиковаться через **Managed Google Play / приватное или внутреннее распространение**, требование по удалению аккаунта, а вместе с ним и значительная часть анкет, снимается или упрощается. Если публиковаться **публично** — понадобится веб-страница запроса на удаление данных и внятный ответ в анкете Data deletion. Это решение по способу публикации стоит принять до подачи, оно определяет объём оставшейся работы.

## 8. Scanner / Web Scanner

**Это ключевое недоразумение, которое нужно снять: в MobileWash нет ни QR-, ни штрихкод-, ни камера-сканера, ни WebView.** «Сканер» здесь — это **сканер локальной сети**, ищущий серверы автомоек по IP. Камера не используется нигде, разрешение `CAMERA` не запрашивается и в манифесте отсутствует.

Ветка `remove-web-scan` и коммит `df867d1` «Skip host scan screen on web» относятся к тому, что **на web-сборке экран сканирования убран** — в браузере приложение всегда обслуживается рядом со своим backend, сканировать нечего.

### Полный поток [ПРОВЕРЕНО по коду]

```
Запуск приложения
  └─ main.dart → Application.dart:52
        kIsWeb ? WebStartupPage : Home      ← развилка, введённая этой веткой

(A) Android / desktop → lib/mobile/pages/home.dart
  1. _bootstrap()                                    home.dart:71
       BackendHostStore.read()  → SharedPreferences['BackendHost']
  2. _refreshNetworkInfo() → LocalNetworkScanner.getNetworkInfo()
       NetworkInterface.list(IPv4, без loopback и link-local)
       фильтр _isUsablePrivateIPv4: 10/8, 172.16–31/12, 192.168/16
       сортировка _addressScore: приоритет wlan/wifi, затем 192.168.*, затем 10.*
  3. Если сохранённый хост есть → probeHost(savedHost)
       BackendBootstrap.validate → GET http://<host>:8020/ping, timeout 2 с
       200 → сразу _openServer() → переход на /mobile/auth
  4. Иначе _findServers() → LocalNetworkScanner.scan()
       _scanCandidates: <prefix>.1 … <prefix>.254, минус собственный адрес
       батчи по 32 (concurrency), timeout 800 мс на хост
       IOClient: connectionTimeout = idleTimeout = timeout, maxConnectionsPerHost = 1
       Stream<LocalNetworkScanUpdate> → setState → прогресс «N / 254»
  5. Тап по найденному хосту → _openServer(host)
       BackendHostStore.save(host)
       Navigator.pushNamed('/mobile/auth', arguments: 'http://<host>:8020')

(B) Web → lib/mobile/pages/web_startup.dart
  1. BackendConfig.webBaseUrl
       dart-define api_base_url, если задан
       иначе Uri.base.host + порт 8020, схема наследуется от страницы
  2. BackendBootstrap.validate(baseUrl) → GET /ping
  3. 200 → pushReplacementNamed('/mobile/auth')
     иначе → экран _StartupFailure с показом URL и кнопкой «Подключиться»
```

Разрешений сканеру не нужно: это обычные HTTP-запросы, покрытые `INTERNET`. Разрешение на доступ к локальной сети в Android не требуется (в отличие от iOS, которого в проекте нет).

**Важное про production-конфигурацию:**

* `build.sh` вызывает `flutter build apk --dart-define-from-file=build_config.json`, но **`build_config.json` в проекте нет** — есть только `build_config.sample.json` со всеми пустыми значениями. `Dockerfile.android`, которым собран текущий APK, `--dart-define-from-file` **не передаёт вообще**, то есть `api_base_url` пуст.
* Для Android это не проблема: там base URL всегда формируется из выбранного хоста, а `defaultScanHost = 'localhost'` используется только как фолбэк при пустой строке. **Localhost, dev- или staging-адреса в Android-сборку не попадают [ПРОВЕРЕНО].**
* Для web-сборки пустой `api_base_url` означает, что backend берётся с origin страницы — это осознанное решение, задокументированное в `web_startup.dart:6–7`.

**Транспорт и надёжность:**

* **HTTP, не HTTPS.** Wash-сервер — LAN-устройство, `network_security_config.xml` разрешает cleartext глобально (`cleartextTrafficPermitted="true"` в `base-config`) с комментарием, объясняющим почему. Для сканирования произвольных адресов подсети ограничить домены действительно нельзя.
* **Авторизация — PIN в заголовке `Pin` в каждом запросе** (`lib/Common/lcw_common.dart:11`). Ни токенов, ни refresh-токенов, ни сессий. Обработки `401` как отдельного сценария (принудительный разлогин) нет.

* **Retry-логики нет** нигде. Для LAN-приложения это приемлемо.
* **Offline-режима нет**: без сервера приложение бесполезно по замыслу.

## 14. Ошибки и потенциальные crash-сценарии

### 14.1 Утечка бесконечного опроса сервера — **самый серьёзный дефект в коде**

**`lib/repository/lea_central_wash_repo/repository.dart:43–48` и `:50–60`**

```dart
void _prepareStatusRefresh() {
  refresh = Future.delayed(refreshDelay, () async {   // 1,5 с
    await updateStatus();
    _prepareStatusRefresh();                          // ← рекурсия без условия выхода
  });
}

@override
void dispose() {
  _stations.dispose(); ...                            // ← цикл не останавливается
}
```

`dispose()` закрывал `ValueNotifier`-ы, но **не останавливал цикл**. Последствия, все три реальные:

1. `updateStatus()` продолжает писать в уже закрытые `ValueNotifier` → `FlutterError: A ValueNotifier<…> was used after being disposed`;
2. каждая неудачная попытка входа создавала новый `LeaCentralRepository` (`auth.dart`) со своим циклом — **циклы накапливались**, и сервер получал в 2, 3, 5 раз больше запросов;
3. `_hashes` и `_discount` вообще не освобождались в `dispose()`.

**Исправлено:** добавлен флаг `_disposed`, проверяемый и до, и после `await` в цикле и в начале `updateStatus()`; `dispose()` сделан идемпотентным и освобождает все notifier-ы.

Он должен возвращать результат или бросать исключение, а показ ошибки принадлежит слою экрана, который умеет проверить `mounted`. Это самый крупный технический долг проекта, но **не блокер публикации**.

## 15. Что мешает публикации

Только подтверждённые блокеры.

1. **Release-сборка подписана отладочным ключом.** `CN=Android Debug, O=Android, C=US`, SHA-256 `22:19:76:…:0B:9F` — извлечено из собранного APK. Причина: нет `android/key.properties`, `build.gradle:88–92` молча откатывается на debug-конфиг. Google Play отклоняет такие загрузки. *Исправить может только владелец: создать upload keystore и положить `key.properties`. В рамках аудита добавлена защита — AAB-сборка теперь падает с явным сообщением вместо молчаливого отката.*

2. **AAB ни разу не собирался.** В `build/app/outputs/` есть только `apk/`, `bundle/` отсутствует. Ни `build.sh`, ни `build_apk_in_docker.sh`, ни `Dockerfile.android` не собирают bundle. Google Play распространяет приложения через AAB. Сборка AAB — непроверенный путь, и её нужно прогнать до подачи.

3. **Нет Privacy Policy.** Ни документа, ни URL, ни экрана — подтверждено полным поиском по репозиторию. Play Console требует публичную ссылку на политику конфиденциальности для всех приложений; без неё релиз не отправляется. *Требует создания документа и его публикации — вне кода.*

4. **~~`REQUEST_INSTALL_PACKAGES` без допустимого сценария~~ — устранено в этой сессии.** Было блокером: Play допускает это разрешение только для браузеров, мессенджеров с вложениями, файловых менеджеров, enterprise MDM, бэкапа/восстановления и переноса устройства. Самообновление APK с GitHub в перечень не входит, а код, который его использовал, оказался недостижим. Разрешение удалено из обоих манифестов.

## 16. Что желательно исправить перед публикацией

1. **Перенести `versionCode`/`versionName` в источник, который есть в git.** Сейчас они читаются из `android/local.properties`, а файл не версионируется — на чистом клоне соберётся `versionCode 1`, и Play отклонит загрузку как более старую.
2. **Проверить edge-to-edge на Android 15/16.** При targetSdk 35+ режим принудительный, а в приложении нет ни `enableEdgeToEdge`, ни работы с insets. Нужен прогон на устройстве: AppBar, Drawer, нижние кнопки диалогов.
3. **Собрать AAB и проверить, что он ставится и запускается** — путь ни разу не пройден.
4. **Решить способ публикации: публично или через Managed Google Play / внутреннее распространение.** Это определяет, нужны ли веб-страница удаления аккаунта, расширенная анкета Data Safety и App access instructions. Для операторского приложения приватное распространение выглядит уместнее.
5. **Подготовить App access instructions.** Модератор без wash-сервера в сети увидит пустой экран «Серверы не найдены» и может отклонить приложение как нерабочее. Нужны либо демо-доступ, либо подробное объяснение, либо демо-режим.
6. **Добавить ручной ввод адреса сервера** — запасной путь, когда автопоиск не срабатывает.
7. **Разобрать оставшиеся пустые `catch`** (14.5) — каждый потенциально прячет неработающую кнопку.
8. **Обработать `401` отдельно** — возврат на экран входа вместо generic-ошибки.
9. **Прогнать `flutter analyze` и разобрать `use_build_context_synchronously`** (18 мест).
10. **Решить вопрос казахского языка** для публикации в РК.
11. **Сделать окружение сборки воспроизводимым.** `flutter.sdk` указывает во временный каталог, `local.properties` не в git, CI нет. Зафиксировать версию Flutter (fvm или `Dockerfile.android` как единственный официальный путь сборки) и перестать зависеть от того, что стоит на конкретной машине.
12. **Убрать шаблонные заглушки**: README, `web/manifest.json`, TODO в `build.gradle:60`, файл `pubspec (for Linux build).yaml`.

## 18. Финальный статус

### 🔴 Не готов к отправке — имеются блокирующие проблемы

Основание — три подтверждённых блокера из раздела 15: отладочная подпись release-сборки, ни разу не собиравшийся AAB и полное отсутствие Privacy Policy. Четвёртый блокер (`REQUEST_INSTALL_PACKAGES`) устранён в ходе аудита.

Формулирую честно: **это не «плохой проект»**. Техническая база в порядке — targetSdk уже соответствует требованию 2026 года, 64-бит есть, R8 работает, устаревших API после апгрейда не осталось, локализация полная, секретов в репозитории нет. Блокеры — организационные и конфигурационные, а не архитектурные. После создания keystore, публикации политики конфиденциальности и одной успешной сборки AAB статус переходит в 🟡.

Отдельно: одобрение приложения — решение Google, и никакой аудит его не гарантирует. Здесь оценивается только техническая готовность к отправке.
